# ShopCoursework

Учебный интернет-магазин на ASP.NET Core MVC. В проекте есть каталог товаров, корзина, оформление заказов, личный кабинет с адресами доставки и панель администратора для управления товарами и вариантами одежды (SKU, размер, цвет и остаток).

## Технологии

- .NET 8 / ASP.NET Core MVC
- Entity Framework Core 8
- SQLite
- ASP.NET Core Identity
- Bootstrap 5

## Требования

- .NET SDK 8.0.426 или совместимая версия .NET 8
- Инструмент `dotnet-ef` версии 8.x для создания базы данных из миграций

## Запуск

Из корня проекта выполните:

```bash
dotnet restore
dotnet tool install --global dotnet-ef --version 8.0.0
dotnet ef database update
dotnet run
```

Если `dotnet-ef` версии 8 уже установлен, повторно устанавливать его не нужно. После запуска откройте URL, указанный командой `dotnet run`.

База SQLite по умолчанию создаётся в файле `shop.db` в корне проекта. Строка подключения задаётся параметром `ConnectionStrings:DefaultConnection` и может быть переопределена через переменную окружения `ConnectionStrings__DefaultConnection`. В базу миграцией добавляется небольшой набор демонстрационных товаров. Файл базы данных не хранится в Git.

## Настройки

В `appsettings.json` задаются название магазина и формат валюты:

```json
"Store": {
  "Name": "ShopCoursework",
  "CurrencyCode": "RUB",
  "Culture": "ru-RU"
}
```

`Name` отображается в шапке сайта и заголовке вкладки. `CurrencyCode` задаёт код валюты для форматирования в корзине, а `Culture` — локаль отображения цен. При смене валюты укажите соответствующие друг другу код валюты и культуру.

Параметр `AdminEmail` задаётся переменной окружения `AdminEmail` и должен содержать email учётной записи, которой нужно выдать роль администратора. Не добавляйте реальный email администратора в `appsettings.json` или Git. Чтобы настроить администратора в чистой базе:

1. Запустите приложение и зарегистрируйте учётную запись с нужным email.
2. Остановите приложение и задайте переменную окружения `AdminEmail` для процесса приложения.
3. Запустите приложение снова — при старте существующему пользователю будет назначена роль `Admin`.

Статус готовности приложения и подключения к БД доступен на `GET /health/ready`: `200 {"status":"ok"}` означает, что база доступна; `503 Service Unavailable` — что приложение не готово обслуживать запросы.

Не публикуйте реальные адреса и секреты в общедоступной конфигурации. Для локальных переопределений используйте User Secrets или переменные окружения ASP.NET Core Configuration.

### Запуск через Docker Compose

Требуется Docker Desktop или Docker Engine с Compose v2. Скопируйте `.env.example` в `.env` и при необходимости задайте `ADMIN_EMAIL`, затем из корня проекта выполните:

```bash
docker compose up --build
```

Сайт будет доступен на `http://localhost:8080` (порт меняется через `SHOP_PORT` в `.env`). При первом запуске контейнер применит EF Core-миграции к SQLite. База, файлы в `wwwroot/uploads` и ключи ASP.NET Data Protection хранятся в постоянных Docker volumes (`shop_data`, `shop_uploads`, `shop_keys`) и сохраняются при пересоздании контейнера. Ключи Data Protection нужны, чтобы действующие cookie-аутентификации не сбрасывались при перезапуске. Не удаляйте эти volumes, если нужно сохранить данные.

Для остановки используйте `Ctrl+C`, затем `docker compose down`. Health-check доступен по адресу `http://localhost:8080/health/ready`. Значения магазина можно переопределить через `STORE_NAME`, `STORE_CURRENCY_CODE` и `STORE_CULTURE`.

### Загрузка и обработка фото

В Compose запускается внутренний FastAPI-сервис обработки фото; отдельный порт на хост он не публикует. Администратор отправляет изображение как `multipart/form-data` в `POST /Admin/Products/Images` с полем `image`, сессионной cookie и antiforgery-токеном в `RequestVerificationToken`. Допустимы JPEG, PNG и WebP размером до 10 МБ. Сервис проверяет содержимое, удаляет исходные метаданные перекодированием в WebP и создаёт основное изображение (до 1600 px) и превью (до 400 px).

Ответ `200 OK`:

```json
{
  "imageUrl": "/uploads/<id>.webp",
  "thumbnailUrl": "/uploads/<id>_thumb.webp",
  "width": 1200,
  "height": 800
}
```

Клиент может сохранить `imageUrl` в `ImageUrl` товара; загружать и изменять сам товар нужно отдельной админской формой. Некорректное изображение даёт `400`, недоступный обработчик или хранилище — `503`. Файлы находятся в общем постоянном volume `shop_uploads`; Python-сервис не имеет доступа к базе или полномочиям пользователя — авторизация и antiforgery-проверка выполняются в .NET.

### Отчёт по продажам

Администратору доступен read-only JSON-отчёт:

```http
GET /Admin/Analytics/Sales?from=2026-10-01&to=2026-10-31
```

Интерактивная страница отчёта доступна администратору по адресу `/Admin/Analytics/Sales/Page` и через кнопку «Аналитика» в панели навигации. На странице можно выбрать UTC-период до 366 дней, просмотреть сводку, продажи по дням и популярные товары, а также скачать тот же отчёт в CSV.

`from` и `to` обязательны и задаются в формате `YYYY-MM-DD`. Обе UTC-даты включаются в отчёт; максимальная длина периода — 366 дней. Ответ содержит сводку, дневные агрегаты и до 10 популярных товаров:

```json
{
  "from": "2026-10-01",
  "to": "2026-10-31",
  "currencyCode": "RUB",
  "summary": {
    "orders": 12,
    "revenue": 42000.00,
    "paidRevenue": 18000.00,
    "unitsSold": 17
  },
  "daily": [
    { "date": "2026-10-01", "orders": 2, "revenue": 7000.00, "unitsSold": 3 }
  ],
  "topProducts": [
    { "productId": 1, "productName": "Джинсы", "unitsSold": 5, "revenue": 17500.00 }
  ]
}
```

Денежные значения указаны в валюте `Store:CurrencyCode`. В отчёт входят заказы, не имеющие текущий статус «Отменён». `revenue` — сумма оформленных заказов вне зависимости от оплаты; `paidRevenue` учитывает только заказы с отмеченным статусом оплаты. Названия и цены товаров берутся из снимков позиций заказа, а для товара без снимка имени используется подпись `Товар №<id>`. Данные покупателей, адреса и контакты в ответ не включаются. Отчёт формируется .NET-приложением из SQLite; Python-сервису база и пользовательские данные не передаются.

Чтобы открыть отчёт в табличном редакторе, администратор может скачать CSV за тот же период:

```http
GET /Admin/Analytics/Sales/Csv?from=2026-10-01&to=2026-10-31
```

CSV содержит строки итога, дневных агрегатов и топ-10 товаров; суммы записываются с точкой и двумя десятичными знаками. Файл кодируется UTF-8 с BOM для корректного отображения русского текста, а текстовые ячейки экранируются и защищаются от выполнения формул табличными редакторами. Используются те же ограничения дат и прав администратора, что и для JSON-отчёта.

Дополнительные вычисляемые показатели предоставляет `GET /Admin/Analytics/Sales/Insights` с теми же `from` и `to`. .NET сначала формирует такой же проверенный агрегированный отчёт, затем передаёт его внутреннему FastAPI-сервису; прямого публичного маршрута к Python нет. Ответ содержит средний чек, среднюю выручку на календарный день, лучший день, изменение средней дневной выручки между первой и второй половинами периода и долю выручки топ-10 товаров. Денежные показатели аналитики сериализуются строками с двумя знаками после запятой; проценты — строками с одним знаком. Для однодневного периода тренд помечен `insufficient_data`, нулевая выручка первой половины и продажи во второй — `new_sales`. Если сервис аналитики недоступен, endpoint возвращает `503`; базовый отчёт `GET /Admin/Analytics/Sales` продолжает работать.

## Основные возможности

- просмотр каталога, отдельная страница товара и добавление выбранного варианта в корзину;
- настройка таблиц размеров по меркам для каждой модели и рекомендация по доступным вариантам;
- оформление заказа и просмотр заказов в личном кабинете;
- регистрация, вход, смена пароля и редактирование профиля;
- добавление и удаление адресов доставки;
- выбор адреса при оформлении заказа с сохранением его снимка в заказе;
- оплата наличными при получении без подключения платёжного сервиса;
- добавление, изменение и удаление товаров в панели администратора;
- управление вариантами товара, SKU и складскими остатками;
- проверка и списание остатков при оформлении заказа;
- просмотр заказов в админке, переходы статусов и отмена с возвратом остатка;
- история статусов и оплаты заказа в личном кабинете и админке;
- фильтрация админского списка заказов по статусу, оплате, номеру заказа и email покупателя;
- просмотр агрегированного отчёта по продажам для администратора;
- отмена покупателем нового или подтверждённого заказа до передачи в доставку;
- проверка antiforgery-токенов для POST-запросов.

Администратор управляет вариантами товара на странице «Варианты и остатки». У каждого SKU должен быть уникальный код, размер, цвет и неотрицательный остаток. Цена берётся у базового товара. При оформлении заказа сервер повторно проверяет и атомарно списывает остаток; клиентская корзина не является источником истины по наличию. В заказе сохраняются снимки названия, цены, SKU, размера, цвета и выбранного адреса доставки на момент покупки.

### Подбор размера одежды

В админке откройте `/Admin/Products/{id}/SizeGuides` и задайте для каждого размера модели включительные диапазоны мерок груди, талии и бёдер в сантиметрах (30–200). Размер должен совпадать с размером складского варианта. Для изменения или удаления диапазона используйте кнопки в таблице размеров.

Публичный endpoint рекомендации:

```http
POST /Products/{productId}/SizeRecommendation
Content-Type: application/json

{ "chest": 96, "waist": 74, "hips": 100 }
```

Достаточно указать хотя бы одну мерку; каждая указанная мерка должна попасть в диапазон размера. В ответ попадают только активные варианты с положительным остатком. Если подходят несколько размеров, первым выбирается размер с большим суммарным остатком, затем меньший стандартный размер. Ответ содержит `recommendedSize`, остаток выбранного размера, список совпавших доступных размеров и пояснение. При отсутствии таблицы, совпадений или остатков `recommendedSize` будет `null`. `400` означает некорректные/отсутствующие мерки, `404` — неизвестный товар.

Мерки принимаются только в теле запроса, не сохраняются в БД и не включаются в ответы; endpoint возвращает `Cache-Control: no-store`. Это ориентировочная подсказка, не гарантия посадки. Администратор задаёт таблицу для каждой модели индивидуально.

Каталог на главной странице (`GET /`) поддерживает поиск по названию и описанию, фильтрацию по размеру и наличию, сортировку по цене и рейтингу, а также постраничный вывод по 8 товаров. Номер страницы меньше 1 отклоняется с `400 Bad Request`, слишком большой номер ограничивается последней страницей. Страница товара доступна по `GET /Products/{id}` и показывает описание, фото, активные варианты с остатками, таблицу мерок и подбор размера. После рекомендации доступный вариант рекомендованного размера автоматически выбирается в селекторе; покупатель может поменять цвет и добавить точный SKU в корзину. Серверная проверка наличия и остатков при checkout остаётся обязательной и не доверяет данным браузерной корзины.

### Уведомление о поступлении размера

Вошедший пользователь может подписаться со страницы товара на размер из её таблицы мерок, если активного варианта этого размера сейчас нет в наличии. Подписка привязана к учётной записи, товару и размеру; повторные подписки объединяются. При добавлении варианта с остатком или при включении/пополнении складского варианта система фиксирует поступление. Уведомление показывается в личном кабинете на вкладке «Поступления»; email не отправляется. Пользователь может удалить подписку. Это одно уведомление на одну подписку; после удаления можно подписаться снова. Если остаток закончился до просмотра уведомления, кабинет показывает, что размер поступал, но сейчас недоступен. Данные о мерках не нужны и не сохраняются.

Для защиты от повторной отправки checkout-клиент может передавать уникальный заголовок `Idempotency-Key` длиной 16–128 символов (`A-Z`, `a-z`, цифры, `.`, `_`, `-`). Успешный ответ имеет формат `{"orderId": 123, "duplicate": false}`; повтор с тем же ключом и составом возвращает тот же `orderId` с `duplicate: true` и не списывает остатки повторно. Повторное использование ключа для другого адреса или состава возвращает `409 Conflict`. Ключ следует сохранять при повторах сетевого запроса и создавать новый для следующего намеренного заказа. Для обратной совместимости запросы без этого заголовка пока принимаются без гарантии идемпотентности.

Админские операции создания и изменения товара проверяют ограничения полей на сервере. URL изображения должен быть HTTP(S) или локальным путём. SKU нормализуется в верхний регистр и остаётся уникальным; размер и цвет обязательны, складской остаток не может быть отрицательным.

Пользовательские формы также проверяются на сервере: имя и фамилия — до 100 символов, телефон — до 32, название адреса — до 80, город — до 100, улица — до 200. Пароль при регистрации или смене должен содержать 6–100 символов.

## Контракт для фронтенда

Сейчас приложение работает как ASP.NET Core MVC, а не как отдельный REST API: каталог (`GET /`), личный кабинет (`GET /Account/Index`) и админка возвращают HTML. Формы регистрации, входа, профиля, адресов и админки отправляются как `application/x-www-form-urlencoded` и после обработки обычно получают redirect. Из этих маршрутов только оформление заказа ниже предназначено для вызова JavaScript-клиентом и возвращает JSON.

### Оформление заказа

`POST /Orders/Create` — JSON-запрос от вошедшего пользователя. Браузер должен отправлять запрос с той же сессионной cookie и antiforgery-токеном. Токен выдаётся в скрытом поле `__RequestVerificationToken` на странице корзины (`GET /Cart`); передавайте его в заголовке `RequestVerificationToken`.

```http
POST /Orders/Create
Content-Type: application/json
RequestVerificationToken: <token из страницы корзины>
Idempotency-Key: checkout-2026-10-19-0001
```

```json
{
  "addressId": 12,
  "lines": [
    { "variantId": 34, "qty": 2 }
  ]
}
```

`addressId` должен принадлежать текущему пользователю. `lines` содержит от 1 до 100 строк; `variantId` — положительный ID активного варианта, `qty` — от 1 до 99, суммарно не более 99 единиц на один вариант. Клиент не передаёт цену: сервер берёт актуальные цены и наличие из базы.

`Idempotency-Key` необязателен для совместимости, но рекомендуется: 16–128 ASCII-символов из `A-Z`, `a-z`, цифр, `.`, `_`, `-`. При сетевой ошибке повторяйте тот же ключ и тот же payload; для нового намеренного заказа создавайте новый ключ. Тот же ключ и payload возвращают исходный заказ, не списывая остатки повторно. Тот же ключ с другим адресом или составом возвращает конфликт.

Успешный ответ — `200 OK`:

```json
{ "orderId": 123, "duplicate": false }
```

Для успешного повтора `duplicate` будет `true`. Ошибки возвращаются как JSON с полем `message`:

| HTTP | Значение |
|---|---|
| `400 Bad Request` | Некорректная корзина, адрес или `Idempotency-Key` |
| `401 Unauthorized` | Пользователь не вошёл в систему |
| `409 Conflict` | Вариант недоступен/остатка недостаточно, ключ уже использован с другим payload или SQLite занят конкурентной операцией |

Antiforgery-проверка может отклонить запрос с неверным или отсутствующим токеном (`400`). После успешного оформления заказ сохраняет снимок адреса, состава и цен; способ оплаты — наличными при получении.

### MVC-формы и будущий отдельный API

`POST /Account/UpdateProfile`, `/Account/ChangePassword`, `/Account/AddAddress`, `/Account/DeleteAddress/{id}` и `/Account/CancelOrder/{id}` — cookie-аутентифицированные MVC-формы с antiforgery-защитой. Они перенаправляют обратно в личный кабинет и передают сообщение через `TempData`, а не возвращают JSON. Адресные поля: название до 80, город до 100, улица до 200 символов. Профиль: имя и фамилия обязательны (до 100), телефон до 32 символов.

Маршруты `/Admin/Products/*` и `/Admin/Orders/*` также являются HTML/MVC-интерфейсом, требуют роль `Admin` и antiforgery-токен. Их ответы и редиректы не являются контрактом JSON.

Если фронтенд будет размещён на отдельном origin или ему понадобятся JSON-каталог, профиль, адреса и админские операции, нужно отдельно спроектировать REST API, CORS и способ аутентификации. Нынешние MVC-маршруты не следует считать такими API.

В админке заказы проходят этапы «Новый» → «Подтверждён» → «Отправлен» → «Доставлен». После доставки администратор отдельно отмечает получение оплаты наличными. Покупатель или администратор может отменить новый или подтверждённый заказ; отмена атомарно переводит его в статус «Отменён» и возвращает зарезервированные варианты на склад. Повторная отмена и отмена уже отправленного или доставленного заказа не выполняют переход и не меняют остатки.

Список `/Admin/Orders` показывает до 10 заказов на странице. Его можно отфильтровать по статусу заказа и оплаты, а также найти заказ по номеру или email покупателя. Фильтры передаются в query string, могут сочетаться и сохраняются при перелистывании; недопустимые значения статусов и номера страницы меньше 1 отклоняются с `400 Bad Request`.

Для каждого заказа сохраняется история создания, смены статуса, получения оплаты и отмены с датой и временем. Она отображается в личном кабинете покупателя и в админке. При применении миграции существующие заказы получают исходную запись текущего состояния; более ранние изменения, которые не сохранялись, восстановить нельзя.
